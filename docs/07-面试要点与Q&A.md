## 1. 项目一句话简介

> 一个「**训练 → 推理 → 可视化 → 洞察**」全链路的电商用户流失预测系统：
> PyTorch 训练 ANN-MLP 模型，FastAPI 提供实时预测接口，Vue3 呈现科技风数据大屏，并把数据翻译成可执行的运营洞察。

## 2. 30 秒电梯陈述（STAR）

- **背景**：电商平台用户流失是营收风险，希望提前识别高流失风险用户进行干预。
- **任务**：构建流失预测模型 + 让业务方「看得懂、用得上」。
- **行动**：
  1. 用 PyTorch 训练 ANN-MLP，完整预处理管线（编码/标准化/分层抽样），早停防过拟合；
  2. FastAPI 做训练/推理解耦，产物 pkl/pth 统一持久化，保证训练推理同源；
  3. Vue3 + ECharts 打造科技风大屏（含自研星空/流光氛围层），6 大面板 + 自动洞察；
- **结果**：准确率 92.16%、AUC 0.9154；沉淀 8 个分析接口与一套可复用的大屏组件。

## 4. 高频面试题与参考答案

### 模型 / 算法方向

**Q1：为什么用 ANN-MLP，不用 XGBoost / LightGBM？**
表格数据上 GBDT 往往更强。本项目选 MLP 出于三点：① 需要演示深度学习完整链路（反向传播、正则、早停）；② 中小样本下 MLP 已能较好拟合；③ 便于后续扩展。**诚实补充**：真实场景建议与 XGBoost 做对比，MLP 在特征工程充分时也有竞争力。

**Q2：如何防止过拟合？**
四层手段：① **早停**——验证集 Loss 连续 15 轮不降即停止，同时保存最优权重；② **Dropout(0.3)** 随机失活神经元；③ **L2 正则** weight_decay=1e-4；④ **数据层面**分层抽样保证验证集分布稳定、训练集 7 成足够。从 Loss 曲线看训练/验证 Loss 同步下降，无显著过拟合。

**Q3：样本只有 500 条，模型 92% 是不是不可信？**
是的，需要诚实说明：① 数据是模拟数据，特征与标签相关性较强，指标偏乐观；② 真实业务指标通常更低，但**模型评估方法论（分层抽样/混淆矩阵/AUC/早停）是可迁移的**；③ 这也是改进空间，见模型设计文档 §7。

**Q4：类别不平衡怎么处理？**
本项目正负样本接近均衡（49.8% vs 50.2%），无需特殊处理。真实场景若不平衡：① 类别权重 class_weight；② Focal Loss；③ 过采样 SMOTE；④ **优先关注召回率与 AUC 而非准确率**——流失用户漏判代价更高。

**Q5：为什么用分层抽样？**
保证训练/验证/测试三集的正负比例与总体一致，评估更可信；防止随机划分导致某类在测试集过少。

**Q6：BatchNorm 在这里有什么用？**
① 稳定每层输入的分布，允许较大学习率、加速收敛；② 缓解梯度消失；③ 推理阶段 `model.eval()` 会使用运行期统计量（running mean/var），所以推理与训练行为一致。

**Q7：特征顺序为什么重要？**
MLP 是结构化网络，输入向量每一维必须与训练时特征顺序严格一致，否则权重对应的特征错位，输出无意义。用 `feature_cols.pkl` 固化顺序，杜绝手写顺序列表。

**Q8：怎么评估模型好坏的？**
分类任务看四个维度：① **AUC** 0.9154——排序能力；② **准确率** 92.16%；③ **混淆矩阵**分析两类错误；④ **召回率**——流失用户召回 92%，保证高价值「真流失」被抓住。

### 工程 / 架构方向

**Q9：训练和推理为什么解耦？怎么做到的？**
训练是重型离线任务，推理要求低延迟，耦合会导致「训练模型改一下后端就得重发」。做法：训练产出一套文件（pth 权重、scaler、encoders、feature_cols），后端只加载文件、绝不 import 训练脚本。换数据重训即可，前后端零改动。

**Q10：怎么保证训练和推理的预处理一致？**
关键设计：**预处理对象在训练阶段序列化为 pkl，推理阶段反序列化直接复用**。`scaler.transform`、`encoder.transform` 用的是训练时 fit 出来的同一个对象——从根上杜绝「推理时重新 fit」的错误。

**Q11：后端为什么用 FastAPI？**
① 原生 asyncio 异步，适合 IO 密集的推理服务；② Pydantic 自动做请求校验（类型/范围），非法输入直接 400；③ 自动生成 Swagger 交互文档，联调效率高；④ 生态成熟，Uvicorn 部署简单。

**Q12：`torch.load(weights_only=True)` 是什么？**
PyTorch 官方安全建议。默认 pickle 反序列化可能执行任意代码（恶意模型文件攻击）。`weights_only=True` 只允许反序列化张量/容器等安全类型，避免 RCE 风险。

**Q13：前端大屏是怎么做的数据可视化？**
图表用 **ECharts**（标准专业观感），并做了三层工程化：
① 用 `echarts/core` 按需引入 + 注册统一的「tech-dark」科技暗色主题，`manualChunks` 分包控制体积；
② 封装通用 `EChart.vue` 组件，统一处理初始化/option 更新/ResizeObserver 自适应/卸载 `dispose()`；
③ 配置遵循可视化方法论——先选形式再上色、顺序/分类/发散编码分工、环形 2px 表面间隙、CVD 色盲安全色板。
氛围层（星空粒子、流光边框、呼吸光晕）用自研 CSS/Canvas，ECharts 不擅长、也是体现前端功底的亮点。

**Q14：跨域问题怎么解决的？**
开发环境用 Vite 代理：前端 `/api/*` 请求转发到 `127.0.0.1:8000`，同源无跨域；生产环境用 Nginx 反向代理同域托管。后端也配置了 CORS 中间件作为兜底。

**Q15：为什么后端接口统一 `/api` 前缀？**
① 路由语义清晰，前后端约定一致；② 代理转发简单可靠——原样转发不 rewrite，避免路径改写产生 404（这是迭代中踩过的坑）。

### 数据分析方向

**Q16：从数据里发现了什么？**
① 流失本质是「沉默 + 低价值」：距上次下单 >30 天用户流失率 92%，下单频次/消费/活跃与流失强负相关（|corr|>0.6）；② 55+ 与 18-24 年龄段、Social 渠道是高危群体；③ 分层运营建议：沉睡用户召回券、低频用户复购激励、高龄专属客服。

**Q17：洞察是怎么生成的？是硬编码吗？**
规则化自动生成，非硬编码：后端按数据规则（如 `last_buy_days > 30` 的用户群流失率）实时计算流失率与均值偏差，动态生成「沉睡用户风险：流失率 92.2%」这类文案。改数据自动更新。
